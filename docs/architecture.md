# 모아타운 현황지도 상세 설계

- 상태: 지도 구현 전 설계 및 데이터 기반
- 기획: [제품 기획서](product-spec.html) · [데이터 출처와 범위](data-sources.md)
- 범위: 서울시 공식 선정 대상지, 로그인 없는 공개 조회, GitHub Pages
- 범위 제외: 운영진 화면·계정·DB·동의 정보·게시판·AI·자동 수집 배치

## 1. 구성과 선택

```text
서울시·자치구 공고/고시, 공식 조회 데이터
 → 원문과 적용 대상 검토 → 일자별 공개 스냅샷
 → 정적 무결성 검사 → latest.json 포인터 → GitHub Pages
 → 브라우저: 목록과 상세 → 지도 레이어(공간자료가 있는 항목)
```

별도 서버 없이 배포합니다. 이번 단계에서는 정적 진행 현황 페이지와 데이터만 넣습니다. 지도 구현 시 UI와 데이터 검증은 분리합니다. 첫 구현 후보는 가벼운 정적 프런트엔드와 GeoJSON 레이어를 지원하는 지도 라이브러리입니다. 배경지도 사업자는 브라우저 사용 조건, 한국 주소 가독성, 출처 표시와 사용량 정책을 검토해 확정합니다. 정적 경계 렌더링은 배경지도 로딩 성공과 독립적이어야 합니다.

| 대안 | 판단 |
| --- | --- |
| 정적 JSON과 GeoJSON | 채택. 범위가 공개 읽기 전용이고, 버전과 출처를 저장소에서 확인할 수 있습니다. |
| 동적 API와 공간 DB | 보류. 계정·편집·서버 검색이 생기면 검토합니다. 지금은 서버와 권한 관리만 늘어납니다. |
| 배경지도 API에 구역 정보까지 의존 | 제외. 구역을 직접 관리할 수 없고 출처와 과거 상태를 재현하기 어렵습니다. |

## 2. 화면과 선택 상태

| 영역 | 동작 | 장애·빈 상태 |
| --- | --- | --- |
| 서울 전역 지도 | 자치구·모아타운 상태 필터. 축소 상태는 점·군집, 확대하면 검증된 경계와 이름 표시. | 위치 미확인은 목록에만 표시. 배경지도 실패 시 목록에서 탐색. |
| 대상지 목록 | 대상지명·자치구·수록 주소 검색. 지도와 단일 필터 상태 공유. | 결과 없음과 원자료 없음은 다르게 표시. 지번 검색이 포함 판정을 뜻하지 않음. |
| 모아타운 상세 | 관리계획 상태, 공식 선정일, 시·구 원문, 내부 사업구역 목록. | 내부 구역 자료 없으면 미확인. 세부 사업구역이 없다고 단정하지 않음. |
| 사업구역 상세 | 목표 세대수, 최고 지상 층수, 전용면적/주택형, 시공사, 사업 단계. 필드별 출처·기준일·확정성. | 공개 집계의 면적 구간과 개별 주택형 구별. 위 구역 수치를 채워 넣지 않음. |
| 자료 안내 | 갱신일·기준일 구분, 출처 우선순위, 용어와 경계 정확도 설명. | 공개 데이터에 담지 못한 범위도 표시. |

선택한 모아타운을 굵은 외곽선으로, 세부 사업구역을 별도 윤곽선과 라벨로 구분합니다. 승인·확정된 경계와 공식 계획안 경계는 실선·점선 및 라벨로 구분합니다. 사업 단계 색상과 선택 강조는 별개입니다. 리스트 키보드 탐색, 선택 시 상세 제목으로 이동, 닫을 때 이전 초점 복귀를 지원합니다. 모바일에서는 작은 지도 영역을 상세 패널이 가리지 않도록 축소/펼침을 지원합니다. 첫 버전 선택 링크는 프로젝트 하위 경로를 보존하는 쿼리 파라미터 방식(`?town=...&zone=...`)을 권장합니다.

모아타운 관리계획 상태와 개별 사업구역 추진 상태는 별도 열거형으로 관리합니다. 서울시 [모아통합기획 발표](https://www.seoul.go.kr/news/news_report.do?bbsNo=15&nttNo=467904)처럼 병행 절차가 있을 수 있어 진행률 %나 단일 순서로 합치지 않습니다.

## 3. 데이터 계약 v1

| 파일 | 주요 항목 및 규칙 |
| --- | --- |
| `moatown-data/latest.json` | `schema_version`, `snapshot_date`(KST), `coverage`, `files`. 사이트 스냅샷 날짜와 원자료 기준일은 분리. |
| `snapshots/YYYY-MM-DD/towns.json` | 변하지 않는 `id`, `district`, `name`, `address`, 선정일과 그 정밀도, 자료 기준일, 출처, 관리계획 상태, 검증된 대표 위치. 공식 선정 목록 원항목과 제외 기록은 구분. |
| 같은 폴더 `zones.json` | 고정 `id`, `town_id`, 이름, 개별 사업 상태, 계획 수치·주택형·시공사. 필드별 근거와 검증 수준을 별도 보관. |
| 같은 폴더 `boundaries.geojson` | GeoJSON FeatureCollection. `entity_type`, `entity_id`, `source_url`, 기준일, 경계 확정성을 속성으로 둠. EPSG:4326 경도·위도 순서, Polygon/MultiPolygon, 링 폐합 검사. 검증 자료가 없으면 빈 컬렉션. |
| 같은 폴더 `excluded.json` | 제외한 선정 취소 등 공식 사건과 근거. 기본 지도와 목록에는 노출하지 않음. |

ID는 최초 명부 원식별자 기준으로 부여하고, 명칭·주소 변경이나 다음 번 원자료 행번호가 바뀌어도 재부여하지 않습니다. 새 자료와 기존 건은 이름·주소·공고를 대조해 연결합니다. 공식 목록의 모순은 감사용으로 보존하되 지도용 위치로 확정하지 않습니다. 값 미확인은 null, 공식적으로 미선정(시공사 등)은 별도 상태입니다. 일자 미상 자료에 날짜를 만들지 않습니다. 주소 텍스트만으로 임의 중심점이나 경계를 생성하지 않습니다. 검증된 필지 내부점 또는 공식 사업지 도형의 위치 참고점은 `representative_point`에 GeoJSON Point(경도·위도)로, 좌표의 유형·자료 출처·기준일·확인 방법은 `representative_point_evidence`에 기록합니다. 이 점은 사업구역 경계를 대체하지 않습니다.

## 4. 업데이트와 배포

1. 한국시간 날짜 기준으로 공식 원문, 변경 여부, 적용 구역, 공개 재사용 조건을 검토합니다.
2. 날짜 폴더로 스냅샷을 보관합니다. 날짜가 같고 정정이 필요하면 변경 사유를 커밋에 남깁니다.
3. JSON 파싱, 고유 ID, 구역 참조, 확인 가능한 출처, 선정 취소 제외, 경계 자료의 공개 가능 여부를 확인합니다. 포인터와 파일을 같은 변경 단위로 올립니다.
4. GitHub Pages 배포 원본: `main` / `(root)`, Jekyll 변환 없이 정적 제공(`.nojekyll`). 링크와 fetch는 저장소 프로젝트 경로를 보존하는 상대 경로를 사용합니다.
5. 배포 뒤 루트, 기획 HTML, 최신 manifest, manifest의 데이터 파일들을 HTTP로 확인합니다. 잘못된 데이터 공개 시 이전 검증된 스냅샷으로 포인터를 되돌립니다.

나중에 배치는 새 데이터 후보를 생성하는 역할만 맡습니다. 소식은 공식 선정·인가 상태를 자동 덮어쓰지 않고, 운영 승인 뒤 같은 공개 규격으로 배포합니다.

## 5. 구현 순서와 수용 기준

1. **데이터 및 배포 검증**: 프로젝트 경로에 올린 문서와 정적 파일을 검증합니다. 1차 명부와 후속 자료 사이의 누락을 공개합니다.
2. **목록과 상세**: 한 번의 검색으로 대상지 접근, 위치 없는 항목도 상세 가능. 필드별 출처 열기와 모바일·키보드 확인.
3. **지도**: 줌에 따른 서울/대상지/사업구역 레이어 전환, 구역 선택과 목록 연동, 경계 미확인 대체 상태 확인.
4. **공개 전 검증**: 명부 차이와 경계 공개 권한, 날짜 표시, 정적 경로와 실패 상태, 민감정보 미포함 확인. 최신 서울 전체 명부나 모든 구역 경계가 아직 확보되지 않았다면 부분 데이터임을 명시합니다.
